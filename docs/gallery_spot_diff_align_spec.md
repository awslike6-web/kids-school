## 1. 배경 (왜 필요한가)

부모가 Gemini 같은 AI 편집기에 "다른 곳은 그대로 두고 ①②③만 바꿔 줘"라고 시켜 바뀐 그림을 만들면, 바꾼 내용 자체는 그럴듯하지만 그림이 원본과 맞지 않는다. 2026-10-29 실제 사례(한옥 입체 모형)에서 잰 값은 다음과 같다.

| | 원본 | Gemini 결과 |
| :--- | :--- | :--- |
| 크기 | 1200×710 | 2000×1116 |
| 가로세로 비율 | 1.690 | 1.792 (약 6% 차이 → 빌더가 거부) |
| 구도 | 받침판 전체 | 약 1.63배 확대, 가장자리 잘림 |
| 기타 | | 오른쪽 아래 Gemini ✦ 워터마크, 그림 전체에 다시 그린 미세한 차이 |

같은 날 임시 시험으로 다음 방법이 통한다는 것을 확인했다.
1. SIFT 특징점 매칭(일치 162개, RANSAC 정상값 91개) → 호모그래피로 AI 그림을 원본 구도로 되돌린다 (원본 영역의 97.6%를 덮음).
2. 두 그림의 픽셀 차이에서 덩어리를 찾으면 실제 바꾼 곳(새 비석, 대문 지붕, 개·남자 자리, 왼쪽 처마)과 잡음(위쪽 가장자리, 워터마크)이 함께 후보로 나온다.
3. **부모가 고른 바뀐 곳만 AI 그림에서 가져오고 나머지는 전부 원본 픽셀로 채우면**, 워터마크·가장자리·미세한 차이가 구조적으로 사라지고, 원본과 같은 크기(1200×710)에 차이 4곳만 남는다.

이 작업은 이 절차를 정식 도구로 만드는 것이다.

## 2. A (Action · 목표)

부모가 AI로 편집한 그림 1장과 원본 작품만 주면, 도구가 ① 원본 구도에 자동으로 맞추고 ② 바뀐 곳 후보와 검수 그림을 만들고 ③ 부모가 고른 정답 자리만 원본에 합성해, 기존 등록 명령(`sync_quick_upload.py --diff-file --diff-spots`)에 바로 넣을 수 있는 **원본과 같은 크기의 바뀐 그림 + `spots.json`**을 만든다. 맞춤이 믿을 수 없으면 합성하지 않고 이유를 알려 준다.

## 4. D (Data · 입력·출력 계약)

### 4-1. 명령
```bash
# 1단계: 맞춤 + 후보 + 검수 그림
python -X utf8 scripts/spot_diff_align.py analyze --id art_minsu_20261029_hanok --ai "E:/Downloads/gemini_edit.png"

# (부모가 candidates.json을 고쳐 spots.json으로 저장: 힌트 적기, 필요 없는 후보 지우기, 붙은 후보 나누기)

# 2단계: 정답 자리만 합성
python -X utf8 scripts/spot_diff_align.py compose --id art_minsu_20261029_hanok --ai "E:/Downloads/gemini_edit.png" --spots "<작업폴더>/spots.json"

# 3단계: 기존 등록 명령 (변경 없음, 관제탑 루트에서)
python -X utf8 scripts/sync_quick_upload.py --id art_minsu_20261029_hanok --author "민수" --diff-file "<작업폴더>/hanok_diff.jpg" --diff-spots "<작업폴더>/spots.json"
```

공통 옵션:
- `--id`: 갤러리 작품 ID. `kids/data/gallery-data.js`에서 그 작품의 `imageUrl`을 찾아 로컬 `G:/master-tower/kids-archive/assets/media/...` 경로로 바꿔 **원본으로 쓴다**. 이 파일이 빌더가 만든 최종 원본(EXIF 보정·1200px)이라 좌표 기준과 일치한다.
- `--original <경로>`: `--id` 대신 원본 파일을 직접 줄 때 (아직 등록 전 작품, 시험용). 읽을 때 `ImageOps.exif_transpose`를 먼저 적용한다 (`GEMINI.md` §5-2).
- `--ai <경로>`: AI 편집 그림. PNG·JPG·WEBP. 알파 채널이 있으면 흰 바탕에 합쳐 RGB로 바꾼다. EXIF 회전도 적용한다.
- `--out <폴더>`: 기본값 `uploads/ex/갤러리/_spotdiff_work/{id 또는 원본파일명}/`. `uploads/`는 `.gitignore` 대상이라 커밋되지 않는다. 빌더는 작가 폴더의 맨 위 파일만 훑으므로 이 하위 폴더는 작품으로 잡히지 않는다 (구현 시 다시 확인할 것).

### 4-2. `analyze` 출력 (작업 폴더)
| 파일 | 내용 |
| :--- | :--- |
| `aligned.png` | 원본 크기로 되돌린 AI 그림 (덮지 못한 곳은 투명) |
| `candidates.json` | 바뀐 곳 후보. **`spots` 배열과 같은 형식**에 `hint: ""`. 큰 순서로 최대 8개 |
| `review.jpg` | 한 장짜리 검수 그림: 원본 / 맞춘 AI 그림 / 차이 겹쳐 보기(빨강) + 후보 번호와 원 |
| `report.json` | 품질 수치(§5-3)와 판정 결과 |

`candidates.json` 예:
```json
[
  { "x": 0.567, "y": 0.683, "r": 0.15, "hint": "" },
  { "x": 0.847, "y": 0.672, "r": 0.135, "hint": "" }
]
```
- `hint`가 빈 문자열이라 이대로는 빌더 검증을 통과하지 않는다. **일부러 그렇게 둔다** (부모가 반드시 보고 적게).
- 후보의 `r`은 덩어리를 감싸는 원의 반지름을 짧은 변 비율로 구한 뒤 0.03~0.15로 자른다. 0.15로 잘렸으면 `report.json`에 "후보 N이 커서 두 곳 이상이 붙었을 수 있음"을 적는다.

### 4-3. `compose` 입력·출력
- 입력 `--spots`: 부모가 고친 `spots.json`. 먼저 `validate_diff_spots`로 검증하고, 실패하면 이유를 출력하고 종료 코드 1.
- 출력:
  | 파일 | 내용 |
  | :--- | :--- |
  | `{원본베이스}_diff.jpg` | **원본과 픽셀 크기가 똑같은** 합성 결과. JPEG 품질 92 (빌더가 다시 85로 저장함) |
  | `check.jpg` | 원본 / 합성 결과 / 합성 후 차이 겹쳐 보기 + spots 원 |
  | `report.json` | 갱신된 품질 수치 |
- 등록 명령에 넣을 `--diff-file`, `--diff-spots` 두 줄을 그대로 출력한다.

## 5. S (Spec · 처리 규칙)

### 5-1. 맞춤
1. 두 그림을 회색조로 바꿔 SIFT(`cv2.SIFT_create`, 특징점 최대 4000개)로 찾고, `knnMatch(k=2)` + 비율 검사 0.75로 거른다.
2. `cv2.findHomography(..., cv2.RANSAC, 3.0)`로 AI → 원본 변환을 구한다.
3. **변환 정상 검사**: 배율(정상값 기준 x·y 축 길이 변화)이 0.2~5배 사이이고, 원근 항(`H[2,0]`, `H[2,1]`)의 절댓값이 0.002 이하여야 한다. 벗어나면 `cv2.estimateAffinePartial2D`(회전·배율·이동만)로 다시 구해 보고, 그래도 실패하면 거부한다.
4. `cv2.warpPerspective`(LANCZOS4)로 원본 크기에 맞춘 그림과, 어디를 덮었는지 나타내는 마스크를 같이 만든다.

### 5-2. 후보 검출
1. 덮인 영역에서 원본과 맞춘 그림의 RGB 채널별 차이 최댓값을 구한다. 문턱값 40(옵션 `--threshold`)을 넘는 픽셀을 표시한다.
2. 5×5 열림 연산으로 잡티를 지우고, 짧은 변의 2%만큼 팽창시켜 가까운 조각을 하나로 묶은 뒤 연결 요소로 나눈다.
3. **후보에서 빼는 것**: 넓이가 그림의 0.15% 미만인 덩어리, 덮인 영역의 경계(원본에서 AI 그림이 끝나는 선)에 맞닿은 덩어리. 워터마크는 따로 처리하지 않는다. 후보로 나오면 부모가 지우고, 지운 자리는 합성에서 원본으로 돌아간다.
4. 남은 덩어리를 넓이 순으로 최대 8개까지 `candidates.json`에 적는다. 중심은 덩어리 무게중심이다.

### 5-3. 품질 판정 (실패하면 합성하지 않음)
`report.json`에 모든 수치를 적고, 아래 중 하나라도 걸리면 `analyze`는 검수 그림을 만든 뒤 `❌ [맞춤 실패] 이유`를 출력하고 종료 코드 1, `compose`는 아무 파일도 만들지 않고 종료 코드 1로 끝낸다. 기준값은 파일 맨 위 상수로 둔다.

| 수치 | 기준 | 뜻 |
| :--- | :--- | :--- |
| RANSAC 정상값 수 | 30개 이상 | 맞출 단서가 충분한가 |
| 정상값 재투영 오차 중앙값 | 1.5px 이하 | 맞춤이 정확한가 |
| 바뀌지 않은 영역의 회색조 차이 중앙값 | 12 이하 | 후보 덩어리 밖이 실제로 겹치는가 (AI가 시점·화풍을 바꿨는지) |
| `compose`: 각 spot 합성 영역이 덮인 영역 안에 있는 비율 | 100% | AI 그림이 없는 곳을 합성하려 하지 않는가 |
| `compose`: 후보 수 대비 바뀐 넓이 | 그림의 40% 미만 | 그림 전체를 다시 그린 경우가 아닌가 |

- 실패 메시지는 부모가 읽을 수 있는 말로 쓴다. 예: "AI가 그림을 너무 많이 바꿔서 원본과 맞출 수 없어요. 편집기에 '구도와 시점은 그대로'라고 다시 요청해 주세요."

### 5-4. 합성
1. 다시 맞춤을 계산한다 (결정적이어야 함: `cv2.setRNGSeed(0)`, 같은 입력이면 같은 결과).
2. 차이 덩어리(§5-2의 1~2단계, 빼기 규칙 전)를 구하고, **spots 원(반지름 × 1.2) 중 하나라도 겹치는 덩어리만** 합성 영역으로 고른다. 어떤 spot과도 겹치지 않는 덩어리는 원본으로 되돌아간다.
3. spot 원 안인데 덩어리가 없으면(부모가 직접 찍은 곳) 그 원 자체를 합성 영역으로 쓴다.
4. 합성 영역을 짧은 변의 1.5%만큼 넓히고 가우시안으로 가장자리를 부드럽게 한 알파 마스크로 `결과 = AI×α + 원본×(1−α)`를 계산한다.
5. **색 맞춤**: 영역마다 바로 바깥 고리(폭: 짧은 변 2%)에서 원본과 AI 그림의 채널별 평균·표준편차를 구해, 영역 안 AI 픽셀에 같은 이득·오프셋을 적용한다. 이득은 0.8~1.25로 자른다. 끄는 옵션 `--no-color-match`.
6. α가 0인 픽셀은 **원본과 바이트 단위로 같아야 한다** (JPEG 저장 전 배열 기준). 시험에서 확인한다.

### 5-5. 이동한 물건 경고
- 물건을 옮기면 "새로 생긴 곳"과 "사라진 곳" 두 덩어리가 생긴다. `compose`에서 선택되지 않은 덩어리 중 넓이가 큰 것(그림의 0.5% 이상)이 남아 있으면 `⚠️ 선택하지 않은 큰 변화 N곳은 원본으로 되돌렸어요. 옮긴 물건의 원래 자리였다면 그 자리도 정답으로 넣어 주세요.`를 출력하고 `check.jpg`에 노란 점선으로 표시한다. 종료 코드는 0.

### 5-6. 기타
- 원본 크기와 결과 크기가 다르면 버그다. 저장 직전에 단언한다.
- 결과는 RGB JPEG. 원본이 누끼(투명 PNG) 작품이면 거부한다 (선행 명세서 §3-2-4와 같음).
- 운영 노션·Worker·git에 접근하지 않는다. 네트워크도 쓰지 않는다.
- 출력 문구는 한국어. 콘솔 한글을 위해 `-X utf8` 사용을 문서에 적는다.

## 7. T (Test · 합격 기준)

### 7-1. 자체 시험 `python -X utf8 scripts/verify_spot_diff_align.py`
OpenCV·numpy만으로 그림을 만들어 검사한다 (외부 파일 없이 결정적으로).
1. **정상**: 무늬가 많은 원본(무작위 도형·격자, 1200×800)을 만들고, 1.5배 확대·(−40, +25) 이동·1° 회전·약한 잡음·오른쪽 아래 작은 워터마크를 넣은 "AI 그림"을 만든다. 그 위에 바뀐 곳 3개(색 바꾼 사각형, 새 원, 지운 도형)를 넣는다. `analyze` 후보에 실제 3곳이 모두 포함되고(중심 거리 < 짧은 변 3%), 품질 판정이 통과해야 한다.
2. **합성**: 실제 3곳을 spots로 `compose` → 결과 크기가 원본과 같고, spots 영역 밖(α=0)은 원본과 바이트 단위로 같고, 워터마크 자리는 원본과 같아야 한다.
3. **거부**: 전혀 다른 그림, 원근을 크게 비튼 그림, 70%를 다시 칠한 그림은 각각 맞춤 실패(종료 코드 1)여야 한다.
4. **이동 경고**: 도형 하나를 옮긴 그림에서 새 자리만 spot으로 주면 §5-5 경고가 나와야 한다.
5. **결정성**: 같은 입력으로 `compose`를 두 번 돌리면 결과 배열이 같아야 한다.
6. 시험이 실제로 고장을 잡는지 한 번 확인한다: 합성 마스크를 spot과 무관하게 전체 덩어리로 바꾸면 2번이, 정상 검사를 끄면 3번이 실패해야 한다. 확인 후 되돌린다.
- 이 시험은 OpenCV가 필요해 GitHub Actions 묶음(`node --test`)에 넣지 않는다. OpenCV가 없으면 `건너뜀: opencv-python-headless 미설치`를 출력하고 종료 코드 0. `CORE_CATALOG.md` 「회귀 시험 묶음」 절의 「묶음 밖」 목록에 한 줄 적는다.

### 7-2. 실제 사례 시험 (로컬 전용, 커밋 안 함)
- 표본: `uploads/ex/spotdiff_samples/hanok/original.jpg`(1200×710)과 `gemini_edit.webp`(2000×1116). 한옥 입체 모형 원본과 Gemini 편집본이다. 요청한 변경은 ① 개와 남자 자리 바꾸기 ② 개 뒤 비석을 왼쪽으로 옮기기 ③ 왼쪽 처마 줄이기 ④ 대문 지붕을 기와에서 초가 짚으로.
- `--original`로 `analyze`를 돌려 다음을 확인한다:
  - 품질 판정 통과 (참고값: 2026-10-29 임시 시험에서 정상값 91개, 덮인 비율 97.6%)
  - 후보에 새 비석(왼쪽 아래 약 x 0.16, y 0.68), 대문 지붕(약 0.52, 0.69), 개·남자 자리(가운데 약 0.64, 0.65 / 오른쪽 약 0.85, 0.66)가 포함됨. 대문과 가운데 개는 하나로 붙어 나올 수 있다.
  - 위쪽 가장자리 띠는 경계 규칙으로 후보에서 빠짐
- spots를 대문 지붕·가운데 개·오른쪽 남자·왼쪽 비석 4곳으로 적어 `compose`를 돌린다. `check.jpg`를 **직접 열어 눈으로 확인**한다 (`GEMINI.md` §5-3): 크기 1200×710, 워터마크 없음, 차이가 4곳에만 있음, 합성 경계에 두 겹 선이나 색 띠가 없음. 오른쪽 원래 비석 자리가 선택되지 않았으면 §5-5 경고가 나오는 게 맞다. 그 자리는 개·남자 spot과 겹치는지 보고 판단을 보고서에 적는다.
- 확인한 그림(`review.jpg`, `check.jpg`)은 완료 보고에 첨부하거나 경로를 적되 커밋하지 않는다.

## 9. 부모용 새 절차 (구현 후 `gallery_archive_spec.md` §7로 옮김)

1. **AI 편집**: 원본 사진을 Gemini 등에 주고 "구도·시점·색감은 그대로 두고 ①…②…③…만 바꿔 줘"라고 요청한다. 민서용은 3곳의 크고 분명한 변화, 민수용은 4~5곳의 작은 변화.
2. **분석**: `spot_diff_align.py analyze --id ... --ai ...` → `review.jpg`를 연다. 맞춤 실패가 뜨면 1로 돌아가 다시 요청한다.
3. **정답 고르기**: `candidates.json`을 복사해 `spots.json`으로 저장하고, 필요 없는 후보(워터마크 등)는 지우고, 붙어 나온 후보는 둘로 나누고, 각 곳에 힌트(1~30자)를 적는다. 옮긴 물건은 원래 자리도 넣을지 정한다.
4. **합성**: `spot_diff_align.py compose ... --spots spots.json` → `check.jpg`에서 바뀐 곳만 빨간지 눈으로 확인한다.
5. **등록**: 출력된 `sync_quick_upload.py --diff-file ... --diff-spots ...` 명령을 관제탑 루트에서 실행한다.
6. **확인**: 배포된 갤러리에서 한 판 끝까지 해 본다.
